# A read-only second Claude agent for Terraform, with a separate policy-gated apply runner

LoonVault adds a **second Claude Code agent** ("Agent 2") whose job is to **test the Terraform stacks against real AWS, read-only**, `terraform validate`/`plan`, never `apply`. It runs in its own hardened devcontainer, separate from the agent that authors code and drives GitHub ("Agent 1"). Agent 2's network egress is restricted to the Claude API and the AWS API (plus the Terraform registry/provider download hosts needed for `init`); it has **no path to GitHub**. Its AWS access is a short-lived, **read-only** credential, scoped to the **workloads member account `<MEMBER_ACCOUNT_ID>` only** and to the `infra/loonvault` stack. Mutation is performed by a **separate, non-LLM "apply runner"** that holds the write credential, re-evaluates the plan against an OPA policy gate, and applies only if it passes (see "Credentials" and "How the components communicate"). This is the first deliberate exception to the project's "AWS credentials never enter an agent container" stance (see `docs/devcontainer.md`), and it is bounded precisely so that exception stays small, notably, the *write* credential still never enters an LLM-controlled container.

**Why a second agent at all.** Until now every credentialed Terraform operation ran on the developer's host terminal, with the human shuttling output back to the agent: and that relay is the project's main bottleneck. Agent 2 closes the loop: it owns the `validate`/`plan`/diagnose cycle against AWS so that an agent, not the developer, is the one reading Terraform errors and feeding them back. The developer's role moves up to *architect* (deciding what to build) rather than *courier* (carrying error text between a terminal and a chat window). The gated `apply` is automated by the apply runner, so the developer is removed from that relay too, re-entering only when the policy gate flags a plan.

**Why a separate devcontainer, and not a Claude Code "agent team."** Claude Code's built-in multi-agent feature, agent teams, gated behind `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` ([docs](https://code.claude.com/docs/en/agent-teams)), is the wrong tool here. Teammates are spawned **in-process by a lead session**, coordinate through a local mailbox and task list under `~/.claude/teams/` and `~/.claude/tasks/`, and **inherit the lead's permission mode at spawn time**. It is a single-host, single-trust-boundary, shared-filesystem mechanism with documented limitations ("one team per session", "no nested teams", "permissions set at spawn", "no session resumption with in-process teammates"). None of that survives the boundary we actually need: Agent 2 must run with a *different* network policy and *different* (AWS) credentials than Agent 1, which means a genuinely separate sandbox, not a teammate of Agent 1.

The term "agent teams" is overloaded, and the distinction matters. The *shipped* feature above is in-process. But Anthropic's own largest "agent team" experiment, the [parallel-Claudes C compiler](https://www.anthropic.com/engineering/building-c-compiler) (Nicholas Carlini, Feb 2026; 16 agents, ~2,000 sessions, a 100,000-line compiler that builds Linux), was a *custom research harness*, not that feature. Each agent ran in its **own Docker container** cloning from a shared bare repo; fresh headless sessions were spawned in a `while true` loop (`claude --dangerously-skip-permissions -p "$(cat AGENT_PROMPT.md)"`); and they coordinated purely through **git lock files** (an agent claims a task by writing `current_tasks/<task>.txt`, and git's synchronization forces a colliding agent to pick another), with "*[no] other method for communication between agents*" and "*[no] orchestration agent*." That containerized, file-coordinated topology, not the in-process feature, is the one we follow, because it is the one that tolerates a per-agent trust boundary.

**Credentials: short-lived only, workloads-account only, no static keys.** Anthropic's devcontainer guidance is explicit that container isolation does *not* prevent a compromised session from exfiltrating anything reachable inside it, and therefore: "*Avoid mounting host secrets such as `~/.ssh` or cloud credential files into the container; prefer repository-scoped or short-lived tokens*" ([Development containers](https://code.claude.com/docs/en/devcontainer)). AWS's own Terraform guidance says the same: use IAM roles with temporary credentials, never static access keys, and build the policy up from empty ([Terraform AWS Provider security best practices](https://docs.aws.amazon.com/prescriptive-guidance/latest/terraform-aws-provider-best-practices/security.html)). So:

- **The read/plan role** is delivered as a short-lived **IAM Identity Center** session, the mechanism `plan.md` already uses for terminal applies, and free. IAM Roles Anywhere was rejected: its required CA trust anchor costs ~$400/mo for AWS Private CA (40× the project's `< $10/mo` budget) or means running a self-managed PKI (real operational weight for a solo, ephemeral project), and its only advantage, zero-human-touch credential issuance, is not needed. The developer runs `aws sso login` once at session start; the resulting temporary STS credentials (scoped to a **read-only** role) are injected into Agent 2's container as environment variables, short-lived tokens, never a static key or a mounted long-term credential file (per Anthropic's caveat). The session expires automatically (≤12h). A once-a-day login is a tiny, non-fatiguing touch, not the per-action relay this design exists to kill.
- **The write credential is *not* in Agent 2, it lives in a separate apply runner.** `terraform apply` is gated by a **deterministic plan-policy check, not by human approval.** A human typing `apply` and eyeballing a plan is the *same* discretionary, fatigue-prone control as an in-session permission prompt, if it gets rubber-stamped, it is theater. But a policy gate is only a real control against a *compromised* Agent 2 if Agent 2 cannot step around it, and an Agent 2 that *held* the write credential, running with `--dangerously-skip-permissions`, could simply call `terraform apply` directly and skip the gate. So the write credential and the gated apply are moved out of the injectable agent entirely, into a **separate, non-LLM apply runner** (plain code, a host-side script with the once-a-day Identity Center session; nothing to prompt-inject). The runner consumes the plan Agent 2 hands off, independently re-runs the OPA/Conftest policy set against the plan JSON (`terraform show -json`), and applies **only** if it passes, escalating to the human *only* when a rule trips. The policy **denies** the changes that actually cause harm, replace/delete of stateful resources (RDS, the S3 raw zone, the shared CMK of ADR-0005), IAM or security-group widening, over-budget blast radius. This keeps the principle the rest of the architecture rests on: *the component that can be prompt-injected is never the component that holds the dangerous credential* (the same reason Agent 1 holds GitHub but not AWS). It is also the honest answer to the risk the C-compiler author, a former penetration tester, names, that "*it is easy to see tests pass and assume the job is done*": a green plan is not authorization to mutate the account; a passing *deterministic policy gate, enforced where the agent can't bypass it,* is. The gate is **not new**, it is the Phase 0 OPA-on-plan control the project already plans (`policies/` + `conftest test … plan.json`, PRD stories #17–19), which today is awkwardly pinned to "the developer's local credentials" because the credential-free devcontainer cannot generate a real plan; the apply runner is the credentialed home that control has always needed. Two consequences follow: **(a)** the whole apply path is *hard-blocked* on the Phase 0 OPA deliverable, until it exists, Agent 2 is read-only and apply stays in the developer's terminal; **(b)** the policy set must be **extended** with apply-time destructive-action rules that distinguish a routine ephemeral `destroy` (ADR-0007) from an accidental or injected destructive change inside a normal `apply`, that destructive-action rule is the one genuinely new piece of policy this initiative requires.

Both the read role (Agent 2) and the write role (apply runner) are scoped to the resource types `infra/loonvault` actually declares, in account `<MEMBER_ACCOUNT_ID>` only. Neither can assume into the management account `<MGMT_ACCOUNT_ID>`, touch `infra/org` or `infra/bootstrap`, or act outside `ca-central-1`.

**Network egress.** The container's firewall is default-deny with an allowlist of: `api.anthropic.com` + `downloads.claude.ai` (Claude Code), the AWS service endpoints for `ca-central-1` + `sts.ca-central-1.amazonaws.com`, and `registry.terraform.io` / `releases.hashicorp.com` (provider downloads for `terraform init`). **GitHub is intentionally absent**: Agent 2 has no `gh`, no App key, and no route to `github.com`. Pushing branches and opening PRs remains Agent 1's job alone, keeping the GitHub-capable and the AWS-capable trust boundaries disjoint.

**Permission posture: skip-permissions on the read loop, gated by managed settings.** Agent 2 runs with `--dangerously-skip-permissions` so its `plan`/read loop is genuinely autonomous, that is the whole point of a second agent, and it is the posture the C-compiler harness used (the flag inside a container is what makes a `while true` loop possible). This is defensible under the bank-grade requirement *not* because the flag is safe in isolation, it is not, but because it removes only the weakest control (a discretionary, in-session approval prompt, prone to approval fatigue) while every *mandatory* control above remains: containment, the default-deny egress firewall, short-lived credentials, the deterministic OPA plan-policy apply gate, the ADR-0009 region-lock SCP, a persistent org-level CloudTrail the member account cannot tamper with or read, and the human-reviewed PR path to `main`. "Bank-grade" means layered, least-privilege, contained, audited, reversible automation with a hard gate on irreversible actions, not a human clicking *approve* on every keystroke. The capability is made least-privilege in its own right: `permissions.disableBypassPermissionsMode` is set to `"disable"` in **Agent 1's** managed settings (it is GitHub-credentialed and interactive and must never bypass prompts), so skip-permissions is permitted in exactly one bounded, firewalled, read-only place. The acceptance is contingent, the flag would not be acceptable on `apply` *without the deterministic plan-policy gate in front of it*, with static credentials, without the firewall, or against the management account. This posture and its residual risk are catalogued as **T-052** and **T-053** in `docs/threat-model.md` (§5.15), and auto mode (a classifier reviews each action) is recorded there as the fallback if even read-loop autonomy proves too loose.

**Roles and the human's role.** The two agents are narrow, role-scoped workers, not generic "senior engineers": the consistent recommendation across multi-agent practice. There are three components plus the human, with credentials deliberately disjoint:

- **Agent 1: Reviewer/Integrator** (LLM): authors code, diagnoses failures, opens and comments on PRs. Holds the **GitHub** credential, no AWS.
- **Agent 2: Verifier** (LLM): runs `validate`/`plan` against real AWS and reports what reality did. Holds a **read-only AWS** credential, no GitHub, no write.
- **Apply runner: Executor** (plain code, no LLM, nothing to prompt-inject): holds the **write AWS** credential, enforces the OPA gate, performs `apply`.
- **The human stays the Architect**, holding architecture and product decisions and acting as the escalation target when the policy gate flags a plan.

Each dangerous capability (GitHub write, AWS write) sits in a component that cannot be prompt-injected into using a *different* dangerous capability. This maps onto the Architect / Implementer / Reviewer / Verifier taxonomy common in the field (e.g. the [4-persona system](https://david.coffee/agentic-coding-with-4-personas/)).

**How the components communicate.** Not through any agent-to-agent protocol, Agent 2's firewall makes network messaging impossible by design, and there is no supported cross-container Claude messaging mechanism anyway. Agent 1, Agent 2, and the apply runner share a **host directory** (e.g. `/handoff`), bind-mounted into the agent containers, directly accessible to the host-side runner, which is filesystem state, not egress, so the firewall is irrelevant to it. Agent 2 writes its plan and debug output there; Agent 1 reads the debug output to prepare fixes/PRs. The apply runner does **not** trust Agent 2's artifact: it pulls already-reviewed code from `main`, regenerates its *own* plan, re-runs OPA against that, and applies only if it passes, so a prompt-injected Agent 2 cannot choose what gets applied (the injectable agent is entirely outside the apply trust path). When the runner itself hits trouble, a plan or apply *error*, as opposed to a policy *violation*, it **reports the failure to `/handoff/out/` for the agents to diagnose and never auto-remediates**: reasoning about a failure produces a code change that must re-enter through PR → CI → human merge, never an in-place fix by the component that holds the write credential. (If the runner reasoned about failures it would need an LLM, which would make it prompt-injectable, defeating the entire reason it is separate.) This is the same mechanism Anthropic used in the C-compiler build (agents coordinating through files and git locks) and the same bind-mount pattern this repo already uses for `firewall-extra-domains.txt` and the GitHub App key. Three rules make it reliable and safe:

- **Capture is deterministic, not a model decision.** Agent 2's Terraform runs go through a wrapper (a `just` recipe) that always tees stdout/stderr and the exit code into `/handoff/in/`: the debug output lands on disk regardless of whether the LLM "remembers" to share it.
- **Pickup is autonomous.** Agent 1 watches `/handoff/in/`, via a `/loop` on an interval, or a host-side `inotifywait` that fires `claude -p` on file arrival, reads the Terraform error, diagnoses it against `infra/loonvault`, and either prepares a fix + PR or writes a suggested fix to `/handoff/out/`. The developer is removed from the transport entirely, re-entering only when the plan-policy gate escalates a flagged plan.
- **Handoff files are untrusted data, never instructions.** A compromised Agent 2 could write a prompt-injection payload disguised as a Terraform error. Agent 1 reasons *over* handoff content as data and never executes anything *from* it. The directory is split `in/` (Agent 2 writes, Agent 1 reads) and `out/` (Agent 1 writes, Agent 2 reads) so the trust flow is one-directional per path. This is the same prompt-injection discipline T-051 already applies to repository contents.

The handoff format is designed for an *agent* reader, not a human one: the central lesson of the C-compiler build ("*most of my effort went into designing the environment around Claude… so it could orient itself without me*"). That build also names the LLM-reader failure modes the harness must design around, and they apply directly here. **Context-window pollution:** the wrapper does not dump raw multi-hundred-line plan/apply logs into `/handoff/in/`; it writes a short summary with one grep-able `ERROR <reason>` line per failure, the exit code, and a pointer to the full log on disk, so Agent 1's pickup finds the signal with a single `grep` instead of ingesting the whole transcript. **Time blindness:** long-running Terraform actions emit infrequent progress markers rather than a streaming wall of output. And a standing `README`/progress file in `/handoff/` records current status and dead-ends so a freshly-spawned Agent 1 session orients itself without the developer.

**Relationship to existing decisions.** This narrows, but does not abandon, the `plan.md` locked decision that "CI holds no AWS credentials… all Terraform changes originate from the developer's terminal", that row is updated to read "from the developer's terminal *or* a credential-isolated, plan-gated agent container scoped to one account and one stack." The blast radius of a compromised Agent 2 is bounded by controls that already exist: the region-lock SCP from [ADR-0009](0009-region-lock-scp-at-workloads-ou.md) means even full write access in `<MEMBER_ACCOUNT_ID>` cannot act outside `ca-central-1`, and the management account is exempt from Agent 2 by both account scope and the SCP's own design. One item remains open: the apply path is **sequenced after** two Phase 0 foundation controls, the OPA-on-plan deliverable (the runner's gate) and a **persistent org-level CloudTrail** in the management account covering the Workloads OU (AWS-recommended over a member-account trail precisely because member accounts cannot modify, delete, or read an organization trail, so a compromised member-account agent cannot erase its own audit trail). Neither exists yet, so the apply path cannot precede them. (Resolved above: the runner regenerates its plan from reviewed `main` rather than trusting any artifact from the injectable Agent 2, and reports, never auto-remediates, its own failures.)

**Consequences.** The developer stops being the relay between AWS and the agent, which was the project's slowest step; Agent 2 iterates on `plan` autonomously and surfaces failures to Agent 1 without human shuttling. The accepted cost is a new, deliberate credential exception, an AWS-credentialed agent container now exists, held small by four compounding limits: a read-only self-serve role vs. a human-gated write role, workloads-account-and-`infra/loonvault`-only scope, a firewall with no GitHub path, and the ADR-0009 region lock underneath it all. The container wall is explicitly *not* treated as the security boundary (per Anthropic's own caveat that it doesn't stop in-container exfiltration); the firewall and short-lived tokens are. The shared `/handoff` mount is a new coupling channel between a GitHub-capable and an AWS-capable container, mitigated by the untrusted-data rule and the one-directional `in/`/`out/` split. The threat-model entries for this direction are recorded in `docs/threat-model.md` §5.15 (T-052, T-053) and §8 (residual risk). This ADR records the *direction*; the remaining implementation, the Agent 2 devcontainer spec and its `validate.sh`, the IAM role(s) and Identity Center permission set, the separate apply runner (write credential + OPA gate + `apply`), the `/handoff` wrapper recipe, the `disableBypassPermissionsMode` managed-settings split, and the `plan.md` locked-decision update, is pending and tracked separately.
