# EC2 Instance Connect Endpoint (EICE) for db-init admin access

Database initialisation (`scripts/db-init.sql`: create the `lv_reader`/`lv_writer` roles, grant `rds_iam`, build the schema, seed `FXCADUSD`) runs as the RDS **master** user over an **EC2 Instance Connect Endpoint (EICE)** tunnel to a minimal throwaway bastion EC2. The operator opens an IAM-authenticated, CloudTrail-logged SSH tunnel through EICE and SSH-forwards `localhost:5432` to the RDS endpoint, then runs `db-init.sql` via `psql` against localhost. The EICE, the bastion, and their security groups live in the ephemeral `infra/loonvault` stack and are destroyed with it.

The constraint forcing this: the VPC is fully private (no IGW, no NAT) and RDS is `publicly_accessible = false`, so the operator's laptop has no path to Postgres; and db-init *must* use the master credential, because only the master can create roles and grant `rds_iam` (the application users authenticate via RDS IAM and cannot bootstrap themselves: ADR-0006). The alternatives were rejected: **temporarily making RDS public** exposes the database to the internet during the init window, against the bank-grade posture; an **in-VPC db-init Lambda fetching the master secret** requires re-introducing the Secrets Manager interface endpoint that ADR-0006 removed (and standing endpoint cost); a **Lambda with the secret passed in its invocation payload** writes the master password into Terraform state; **SSM Session Manager** would need three interface endpoints in this no-NAT VPC; and the **RDS Data API** is Aurora-only, not available for this RDS Postgres instance. EICE is AWS's purpose-built path for reaching private resources from an operator's machine without a bastion's public exposure: no IGW/NAT, no public IP, IAM-gated, CloudTrail-audited, and free.

Consequences: RDS never becomes publicly accessible, and the admin access path is itself an auditable control (EICE connections appear in CloudTrail), a positive for the security story. The cost is a small ephemeral bastion EC2 (t4g.nano, pennies per session) and a handful of extra resources in the backend stack. The bastion is a pure TCP relay with no instance profile (it makes no AWS API calls; the master secret is fetched by the operator's own credentials, not the instance). The tunnel uses `sslmode=require` rather than `verify-full` because `psql` connects to `localhost`, so the RDS certificate hostname cannot be verified through the forward, acceptable for a one-off, IAM-gated admin action where the transport is already an authenticated EICE channel.
