# Split ephemeral backend from always-on frontend (separate Terraform stacks)

The infrastructure is split into two independently-applied Terraform stacks with separate state: `infra/loonvault/` (the **ephemeral backend**, RDS, Lambdas, API Gateway, VPC, SQS, the `raw` bucket, and the `main` CMK) and `infra/frontend/` (the **always-on frontend**, currently the public S3 snapshots bucket; later the Next.js static-site bucket and Cloudflare). The backend is applied before an interview and `destroy`ed after; the frontend stays up 24×7 and serves the last-written snapshots via Cloudflare (ADR-0004).

The alternative was a single stack with a targeted teardown (`terraform destroy -target=...` for the backend, or `prevent_destroy` on the snapshots bucket). That was rejected: `prevent_destroy` makes `terraform destroy` fail outright, and `-target` teardown is a long, fragile list that leaves the snapshots bucket as an orphan whose state still references destroyed resources, producing churn on every subsequent plan. Separate stacks make the teardown a clean, whole-stack `just loonvault-destroy` and let the frontend's lifecycle be genuinely independent of the backend's: which is the entire point of the ephemeral-backend design.

The cross-stack dependency is one-way and minimal: the Transform Lambda (backend) writes snapshots to the frontend bucket. The bucket name is deterministic (`loonvault-snapshots`), so the backend references it by name via a local (`local.snapshots_bucket`) rather than a `terraform_remote_state` lookup: writes are identity-based and same-account, so no bucket-policy coordination or remote-state coupling is needed. Consequence: the snapshots bucket name is a contract shared by both stacks; changing the naming convention requires updating both. The `main` CMK lives in the backend stack and is destroyed with it (entering a non-billed pending-deletion window), so the parked baseline is only the bootstrap tfstate CMK (~$1/mo); the snapshots bucket uses SSE-S3, so the frontend has no CMK dependency.
