# RDS IAM authentication for application database users

The Read and Transform Lambdas authenticate to RDS PostgreSQL using **RDS IAM authentication** rather than a username/password stored in Secrets Manager. Each Lambda's execution role is granted `rds-db:connect` on a specific `dbuser` ARN (`lv_reader` for Read, `lv_writer` for Transform), the database users are created with `GRANT rds_iam` and no password, and the handlers generate a short-lived (15-minute) authentication token locally via SigV4 signing at connect time: no Secrets Manager call and no network round-trip.

The alternative, carried through earlier drafts, stored reader and writer credentials in a Secrets Manager secret that the in-VPC Lambdas fetched on cold start. We switched for three reasons. First, **cost and topology**: the in-VPC Lambdas sit in private subnets with no NAT gateway, so reaching the Secrets Manager API required a Secrets Manager interface VPC endpoint (~$7/month per AZ, ~$14.60/month across two AZs while the ephemeral stack runs). IAM auth removes that endpoint entirely because token signing is local, the in-VPC Lambdas now make no AWS API call that needs an endpoint, only the in-VPC connection to RDS and S3 access via the (free) S3 gateway endpoint. Second, **no long-lived secret**: there is no stored database credential to populate, rotate, or leak; a compromised Lambda role can only mint a 15-minute token scoped to one database user. Third, **operational simplicity**: it removes a fragile manual runbook step, previously the operator had to provision the secret value and keep it in sync with the Postgres password set during `db-init`, with nothing linking the two.

The RDS master password remains managed by RDS in Secrets Manager (`manage_master_user_password`, encrypted with the shared CMK) and is never read by the Lambdas: so Secrets Manager is still present in the stack, just off the application data path.

The tradeoffs we accept: RDS IAM authentication is recommended below ~200 new connections per second: not a constraint at portfolio scale, but RDS Proxy would be the production answer for high connection churn. The `rds-db:connect` resource ARN embeds the instance's `DbiResourceId`, which changes on every `destroy`/`apply` of the ephemeral stack, so the IAM policy references `aws_db_instance.main.resource_id` directly and Terraform re-resolves it on each apply. And because the application data path now shows no Secrets Manager usage, that control is demonstrated only by the RDS-managed master secret. SSL/TLS is mandatory for IAM auth, which the existing `sslmode=verify-full` already satisfies.
